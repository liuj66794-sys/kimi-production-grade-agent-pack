# v2.1 Memory Module Specification

## Overview

The Memory module provides context persistence capabilities for the Kimi Agent Pack.
It enables agents to store, retrieve, and query contextual information across
conversation turns and sessions.

## Architecture

```
User Query
    |
    v
Orchestrator (L1)
    |
    +-- Need previous context? --> Memory Sub-Agent
    |                                  |
    |     retrieve(query)              |
    |<---------------------------------+
    |
    +-- Process with context
    |
    +-- New information to persist? --> Memory Sub-Agent
                                         |
               store(key, value, ttl)    |
    <------------------------------------+
```

## Components

### Agent: memory-sub
- **Version**: 2.1.0
- **Type**: Sub-agent
- **Tools allowed**: ReadFile, WriteFile
- **Tools denied**: Shell, SearchWeb, FetchURL, BrowserVisit

### Skills
1. **memory-store**: Store key-value pairs with optional TTL
2. **memory-retrieve**: Retrieve by exact key or semantic query
3. **memory-search**: Search memory with fuzzy/semantic matching

## Memory Types

### Short-Term Memory (Session)
- Scope: Current conversation session only
- Persistence: In-memory, cleared on session end
- TTL: Default 1 hour, configurable
- Use case: Recent context, conversation history references

### Long-Term Memory (Cross-Session)
- Scope: Persistent across sessions per user
- Persistence: Disk-based with encryption
- TTL: Optional (default: no expiry)
- Use case: User preferences, project context, learned patterns

### Working Memory (Agent Internal)
- Scope: Per-agent-instance scratchpad
- Persistence: Ephemeral, lasts for agent lifetime
- TTL: Agent process lifetime
- Use case: Intermediate computation, scratch notes

## Data Model

```json
{
  "memory_entry": {
    "id": "uuid",
    "key": "string (searchable)",
    "value": "any JSON-serializable object",
    "type": "short_term | long_term | working",
    "created_at": "ISO 8601 timestamp",
    "updated_at": "ISO 8601 timestamp",
    "ttl_seconds": "integer or null",
    "expires_at": "ISO 8601 timestamp or null",
    "session_id": "string or null",
    "user_id": "string",
    "tags": ["string"],
    "embedding": "vector (for semantic search)"
  }
}
```

## API Surface

### Store
```
memory_store(key, value, type="short_term", ttl=null, tags=[])
  -> MemoryEntry
```

### Retrieve
```
memory_retrieve(key, type=null)
  -> MemoryEntry | null
```

### Search
```
memory_search(query, type=null, limit=10, semantic=false)
  -> MemoryEntry[]
```

### Delete
```
memory_delete(key, type=null)
  -> boolean
```

### Expire
```
memory_expire(type=null, older_than=null)
  -> count_expired
```

## Hard-Fail Rules

| ID | Rule | Consequence |
|----|------|-------------|
| HF-MEM-01 | Must not lose data during normal store/retrieve operations | Termination |
| HF-MEM-02 | Must not leak memory across user sessions | Termination |
| HF-MEM-03 | Must respect TTL — expired entries must not be returned | Termination |
| HF-MEM-04 | Must encrypt long-term memory at rest | Termination |
| HF-MEM-05 | Must validate JSON-serializability before storing | Termination |

## Security Requirements

1. **Encryption at rest**: All long-term memory entries encrypted with per-user key
2. **Session isolation**: Short-term memory keyed by session_id, no cross-session access
3. **Input validation**: Keys and tags sanitized (max length, no control characters)
4. **Size limits**: Single entry max 1MB, total memory max 100MB per user
5. **Audit logging**: All store/delete operations logged (not content, just metadata)

## Performance SLA

| Operation | Target Latency | Timeout |
|-----------|---------------|---------|
| Store | <50ms | 500ms |
| Retrieve (exact) | <20ms | 200ms |
| Search (text) | <100ms | 1s |
| Search (semantic) | <500ms | 3s |
| Delete | <20ms | 200ms |

## Error Handling

| Error | Response |
|-------|----------|
| Storage full | Reject with "storage limit exceeded"; suggest cleanup |
| Entry too large | Reject with "entry exceeds 1MB limit"; suggest chunking |
| Serialization failure | Reject with "value not JSON-serializable" |
| Encryption failure | Fail closed — do not store unencrypted |
| Retrieve miss | Return null (not an error) |
| TTL race condition | Prefer deletion — expired data is stale data |

## Testing Strategy

1. **Unit tests**: Store/retrieve/search/delete in isolation
2. **TTL tests**: Verify expiry works correctly
3. **Session isolation tests**: Verify cross-session leakage is blocked
4. **Concurrency tests**: Simultaneous store/retrieve from same user
5. **Load tests**: 1000 entries, validate search performance SLA
6. **Security tests**: Verify encryption, attempt session bypass
