# v2.0 L2 Pre-Specification

## Overview

This document defines the pre-specification for the L2 (Level-2) capability layer
of the Kimi Production-Grade Agent Pack. L2 adds specialized sub-agents that extend
the base L1 orchestrator with domain-specific expertise.

## L2 Capability Map

| Capability | Version | Domain | Priority | Spike Order |
|------------|---------|--------|----------|-------------|
| Memory | v2.1 | Context persistence | P0 | Spike #1 (memory-candidate) |
| Slide Maker | v2.2 | Presentation generation | P1 | Spike #2 (slide-outline) |
| Spreadsheet | v2.3 | Data analysis | P2 | Spike #3 |
| Multimodal | v2.4 | Visual analysis | P3 | Spike #4 |

## Capability Priority Rationale

### P0: Memory (Spike #1 — memory-candidate)
- Memory is a foundational L2 capability that benefits ALL other L2 agents
- Without memory, no context persists across sessions
- Memory is the highest risk due to data durability and privacy concerns
- Resolving memory first de-risks all subsequent spikes

### P1: Slide Maker (Spike #2 — slide-outline)
- Slide Maker is the most user-visible L2 feature
- It exercises the orchestrator-to-sub-agent handoff pattern
- Lower risk than memory (stateless output generation)
- Validates the skill-trigger and schema-enforcement pipeline

### P2: Spreadsheet (Spike #3)
- Spreadsheet analysis is a natural extension of data processing
- Builds on patterns established by Memory and Slide Maker
- Moderate risk (file I/O, Shell restrictions)

### P3: Multimodal (Spike #4)
- Visual analysis has the highest uncertainty in output quality
- Depends on upstream image processing capabilities
- Lowest priority due to non-deterministic nature of visual interpretation

## Risk Review Summary

| Spike | Primary Risk | Risk Level | Mitigation |
|-------|-------------|------------|------------|
| memory-candidate | Data privacy, storage durability | High | Ephemeral-only mode, encryption at rest |
| slide-outline | Output format compatibility | Medium | Strict schema validation, markdown fallback |
| spreadsheet | Shell escape, large file OOM | Medium | Shell whitelist, streaming for large files |
| multimodal | Hallucination, false confidence | High | Confidence annotation, hard-fail on fabrication |

## First Spike: memory-candidate

The first L2 spike targets the Memory module because:

1. **Foundation dependency**: All other L2 agents may need persistent context
2. **Risk-driven**: Memory has the highest architectural risk; early validation prevents rework
3. **Isolated scope**: Memory can be tested independently without other L2 agents
4. **Clear success criteria**: Memory has binary pass/fail (store/retrieve works or not)

### memory-candidate Spike Definition

```yaml
spike_id: memory-candidate-spike
objective: Validate basic memory store/retrieve functionality
scope:
  - Short-term memory (session context)
  - Long-term memory (cross-session persistence)
  - Memory query with semantic matching
success_criteria:
  - Can store a key-value pair
  - Can retrieve by exact key
  - Can retrieve by semantic query
  - Memory respects TTL (time-to-live)
  - No data leakage between user sessions
hard_fail:
  - Data loss during normal operation
  - Cross-session data leakage
  - Memory corruption on concurrent access
duration: 1 sprint
```

## Release Gates

Each spike must pass the following gates before proceeding:

1. **Unit smoke test**: All hard-fail rules exercised
2. **Schema validation**: Output conforms to defined JSON Schema
3. **L1 regression**: Existing L1 functionality unaffected
4. **Integration test**: Agent handoff works end-to-end
5. **Security review**: Tool permissions reviewed and approved
